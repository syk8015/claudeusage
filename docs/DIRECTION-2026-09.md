### W2. 간판 지표가 돈의 31.7%에 침묵하면서, 그 돈을 분모에서 빼지 않는다

**(a) 증거** — `src/claudeusage/cc_value.py:855-861` 의 합계 계산


`value --all` 출력을 세어 보면:

- 세션 189개 · 합계 $4,757.19
- **편집 0건인 세션 116개(61%) · $1,507.61 = 전체의 31.7%**
- 그중 $5 이상인 세션이 37개 · $1,392.74

`tot_cost` 에는 이 $1,507.61 이 그대로 들어가고 `tot_surv` 에는 0줄이 들어간다.
결과: 화면에 찍히는 **$0.0739/줄**. 코드가 실제로 나온 세션만으로 계산하면
($4,757.19 − $1,507.61) ÷ 64,404 = **$0.0505/줄**. 간판 숫자가 **46% 부풀어 있다.**

**(b) 왜 문제인가** — 이 프로젝트의 규칙 2 가 "배수를 낼 때 분모를 밝힌다"인데, 정작 자기
간판 숫자의 분자와 분모가 서로 다른 모집단이다. 게다가 이건 단순 계산 실수가 아니라
**측정 대상이 제품 주장과 어긋난다**는 신호다. `--mix` 를 보면 쓰기(Edit·Write)는 비용의
**9.7%**($466.55/$4,789.69)이고 가장 큰 덩어리는 **분류 안 된 셸 실행 46.8%**($2,240.26)다.
`edit_events()`(`cc_value.py:107-128`)는 `toolUseResult` 에 `structuredPatch` 와 `filePath` 가
있는 이벤트만 줍는다. 즉 `sed -i`, heredoc 리다이렉트, `python3 -c` 로 파일 쓰기,
`git apply` 는 **전부 안 보인다.** 이 계정의 주 작업 방식이 바로 그쪽으로 기울어 있다.
"살아남은 코드를 잰다"는 문장은 맞지만, 재는 범위가 돈의 1/10 이다.

또 하나: 생존의 지평선이 **한 세션**이다(`measure()` 가 세션 첫 상태와 끝 상태만 비교).
어제 세션에서 쓴 코드를 오늘 세션에서 지워도 어제 것은 여전히 "살아남음"으로 남는다.
Git AI 대비 차별점으로 내세운 "커밋 없이도 센다"는 사실이지만, 대신 **"오래 살아남았나"를
못 센다**는 반대급부가 문서 어디에도 없다.

**(c) 고치는 비용** — 분모 분리(코드가 나온 세션만으로 $/줄, 나머지는 따로 표시) 4시간.
Bash 로 한 파일 변경을 복원하는 건 훨씬 크다 — `sed`/heredoc 은 결과를 로그에 안 남기므로
사실상 불가능하고, 대안은 **세션 전후로 작업 트리 스냅샷을 찍는 것**이다. 설계부터 새로:
**2~3주.**

### W6. 주간 창 경계가 저자 계정의 리셋 시각으로 못 박혀 있다

**(a) 증거** — `src/claudeusage/cc_chat.py:49-54`

```python
WEEK_ANCHOR = 1789484400.0        # 2026-09-15T15:00:00Z
WEEK = 7 * 86400

def week_of(t):
    return WEEK_ANCHOR + WEEK * ((t - WEEK_ANCHOR) // WEEK)
```

주석이 근거를 밝힌다 — "실측한 `seven_day.resets_at` 이 09-08·09-15·09-22 전부 화요일
15:00Z 였다." 이 계정에서 관측한 값이다. `grep -rn WEEK_ANCHOR src/` 결과 이 값을
데이터에서 다시 뽑는 코드는 없다.

**(b) 왜 문제인가** — 주간 한도 창은 계정마다 언제 처음 한도를 건드렸느냐로 정해진다.
다른 사용자의 리셋이 목요일 03:00Z 라면 `week_of()` 는 그 사람의 한 주를 두 조각으로 잘라
양쪽에 반씩 넣는다. 그러면 `chat` 의 주별 표와 **엔드포인트 정답 대조가 통째로 어긋나는데,
어긋난 티가 안 난다.** 숫자는 그럴듯하게 나오고 검사도 통과한다(W5 의 ±15%p 기준이라면 더).
이건 "틀리면 죽는 버그"가 아니라 "틀려도 사는 버그"라 훨씬 오래 산다.
게다가 고칠 재료가 이미 손에 있다 — `usage` 응답의 `seven_day.resets_at`(`cc_usage.py:154-160`)
과 상태바 표본의 `rate_limits.seven_day.resets_at` 둘 다 실제 리셋 시각을 준다.
쓰지 않고 상수로 박았을 뿐이다.

**(c) 고치는 비용** — 표본에서 관측된 `seven_day` 리셋을 모아 앵커를 유도하고, 하나도
없을 때만 지금 상수를 쓰기. 3시간. `check` 에 "유도한 앵커와 관측 리셋이 어긋나면 실패"
검사 추가 1시간. **합계 약 4시간.**

### W7. 간판 숫자 "1/70"이 코드에 글자로 박혀 있고, 바로 윗줄 자기 적합값과 3배 다르다

**(b) 왜 문제인가** — 이 도구의 사용자는 클로드고, 클로드가 하는 일은
